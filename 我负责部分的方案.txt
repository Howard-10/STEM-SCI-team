## 一、模块定位与技术选型

### 1.1 模块职责

| 序号 | 职责 | 说明 |
|------|------|------|
| 1 | 双层科研知识库 | 全局公共知识库（SSCI论文/理论/量表）+ 用户项目私有知识库（长期记忆载体） |

## 二、全局强制统一数据结构体

### 2.1 项目隔离基础元数据（所有接口必传）

使用 Pydantic 做运行时校验，同时保留 TypedDict 兼容 LangGraph State：

```python
from pydantic import BaseModel, Field
from typing import TypedDict

# === 运行时校验用 Pydantic ===
class ProjectMeta(BaseModel):
    user_id: str = Field(..., description="用户唯一ID，区分不同用户")
    project_id: str = Field(..., description="论文项目唯一ID，私有知识库/长期记忆隔离核心标识")
    run_id: str = Field(..., description="单次会话窗口ID，区分短期会话记忆")

# === LangGraph State 兼容用 TypedDict ===
class ProjectMetaDict(TypedDict):
    user_id: str
    project_id: str
    run_id: str
```

**校验规则：**
- `user_id`：非空字符串，长度 1-64
- `project_id`：非空字符串，格式 `proj_{uuid}` 或等价唯一标识
- `run_id`：每次新会话窗口生成新的 UUID

## 三、嵌入模型选型与切片策略

### 3.1 嵌入模型方案

| 场景 | 模型 | 维度 | 部署方式 | 成本 | 适用 |
|------|------|------|---------|------|------|
| 中文论文/教育文献 | bge-large-zh-v1.5 | 1024 | 本地GPU/CPU | 免费 | 主要场景 |
| 英文SSCI论文 | text-embedding-3-small | 1536 | OpenAI API | $0.02/1M tokens | 辅助场景 |
| 轻量fallback | bge-small-zh-v1.5 | 512 | 本地CPU | 免费 | 低资源环境 |

**推荐方案：** 主用 `bge-large-zh-v1.5` 本地部署，英文论文统一用 `text-embedding-3-small` API。两套嵌入模型的结果存储在同一Chroma中，通过 `embedding_model` 字段标记来源。

**GPU需求：** bge-large-zh-v1.5 模型约1.3GB显存，消费级GPU（RTX 3060 12GB+）即可运行。无GPU时CPU推理约慢5-10倍但仍可用。

### 3.2 科研论文切片策略

```
┌──────────────────────────────────────────────────┐
│                 论文切片层级策略                    │
├──────────────────────────────────────────────────┤
│ Level 1: 文档级  →  title + abstract + keywords   │
│          保留完整摘要用于首轮匹配                   │
│                                                    │
│ Level 2: 章节级  →  Introduction / Method /        │
│          Result / Discussion / Conclusion          │
│          每章一片，保留章节标题作为元数据            │
│                                                    │
│ Level 3: 段落级  →  每个自然段落 + 前文context      │
│          (512 tokens, overlap 128 tokens)          │
│          段落级是最细粒度检索单元                    │
│                                                    │
│ Level 4: 句子级  →  关键主张句 + 证据句             │
│          仅用于 claim-evidence 精确匹配             │
└──────────────────────────────────────────────────┘
```

**实现参数：**
```python
CHUNK_CONFIG = {
    "chunk_size": 512,          # tokens per chunk
    "chunk_overlap": 128,       # overlap tokens
    "separators": ["\n\n", "\n", "。", ".", " "],  # 优先按段落切分
    "keep_section_title": True, # 分片保留父章节标题
    "min_chunk_size": 64,       # 最小分片（过短合并到前一片）
    "max_chunks_per_paper": 200 # 单篇论文分片上限
}
```

### 3.3 公式与表格处理

| 内容类型 | 解析工具 | 存储方式 | 检索方式 |
|---------|---------|---------|---------|
| 普通文本 | pdfplumber | Chunk文本 + 向量 | 语义检索 |
| LaTeX公式 | nougat / Mathpix | LaTeX源码 + 渲染图 | 公式语义embedding + 符号匹配 |
| 数值表格 | camelot / pdfplumber | JSON结构化 | 字段名+数值范围精确匹配 |
| 图片/图表 | pdfplumber提取 | 图片路径 + 图注文本 | 仅图注文本参与检索 |

公式和表格不作为向量检索的主要对象，但作为 `EvidenceItem` 的附件保留，检索命中时一并返回。

## 四、底层公共统一接口（详细实现版）

### 4.1 RAG统一检索接口

```python
def global_retrieve(
    project_meta: ProjectMeta,
    query: str,
    top_k: int = 5,
    search_type: Literal["semantic", "hybrid", "keyword"] = "hybrid",
    filter_theory: Optional[List[str]] = None,
    filter_method: Optional[List[str]] = None,
    include_stale: bool = False
) -> Dict:
    """
    统一检索接口，所有Agent查询文献必须调用此接口。

    检索流程：
    1. 并行检索私有库 + 公共库
    2. 按 source_id 去重（私有库结果优先保留）
    3. MMR 最大边际相关性重排序（λ=0.7，平衡相关性与多样性）
    4. 过滤 verify_status 不足的结果
    5. 附加公式/表格附件

    参数：
    - search_type: semantic(纯向量) / hybrid(向量+BM25混合) / keyword(纯关键词)
    - filter_theory: 按理论标签过滤（可选）
    - filter_method: 按方法标签过滤（可选）
    - include_stale: 是否包含过期版本分片（默认False）

    返回：
    {
        "results": List[EvidenceItem],     # 检索结果
        "metadata": {
            "total_hits": int,             # 总命中数
            "private_hits": int,           # 私有库命中数
            "public_hits": int,            # 公共库命中数
            "retrieval_time_ms": int,      # 检索耗时
            "rerank_applied": bool,        # 是否应用重排序
            "query_rewrite": str           # 查询改写后的文本（如有）
        }
    }
    """
```

### 4.2 检索重排序策略（MMR）

```python
def mmr_rerank(
    query_embedding: List[float],
    candidate_embeddings: List[List[float]],
    candidate_items: List[EvidenceItem],
    lambda_param: float = 0.7,   # 0=最大多样性, 1=最大相关性
    top_k: int = 5
) -> List[EvidenceItem]:
    """
    MMR最大边际相关性重排序。

    公式: MMR = λ·sim(q, d_i) - (1-λ)·max(sim(d_i, d_j))
    其中 d_j 是已选入结果集的文档。

    目的：避免返回5条内容几乎相同的证据，保证检索结果的多样性。
    """
```

### 4.4 分层短期记忆压缩接口

```python
def compress_short_memory(
    state: ResearchState,
    trigger_config: Dict = None
) -> ShortMemorySummary:
    """
    分层压缩短期记忆。仅顶层调度器调用，Agent无权限。

    触发条件（满足任一即触发）：
    1. recent_rounds 超过 max_keep_rounds（默认8轮）
    2. 总token数超过 max_context_tokens（默认8000）
    3. 阶段切换时强制触发

    三层保留策略：
    Layer 1 - 关键决策（Pinned）：
        - 人工审批通过/拒绝节点
        - 阶段确认（current_stage变更）
        - 冲突结论（contradiction_map中的结论）
        → 永不过期，原文保留，不压缩

    Layer 2 - 核心证据引用（Core）：
        - 被 evidence_ledger 引用的对话片段
        - 证据综述Agent产出的核心结论
        → 压缩为一句话摘要 + 保留 evidence_id 指针

    Layer 3 - 过程对话（Process）：
        - Agent推理过程、工具调用日志、非关键交互
        → LLM摘要压缩，保留关键步骤，丢弃冗余细节

    压缩流程：
    1. 扫描 recent_rounds，分类到三个Layer
    2. Layer1直接保留，Layer2提取摘要+指针，Layer3调用LLM摘要
    3. 合并为 ShortMemorySummary，替换旧摘要
    4. 清空已压缩的 recent_rounds，仅保留最新未压缩轮次
    """
    default_config = {
        "max_keep_rounds": 8,
        "max_context_tokens": 8000,
        "compress_model": "gpt-4o-mini",  # 轻量模型做摘要
        "force_on_stage_change": True
    }
```

## 五、个人知识库与论文同步方案【核心新增】

### 5.1 整体思路

用户论文在撰写过程中持续修改，向量库需要保持同步。核心策略是 **分块哈希版本控制 + 增量更新**：

- 每次同步时计算各分片的 SHA256 哈希
- 与上一版本对比，仅重新嵌入变化的分片
- 保留历史版本，支持版本回溯
- 检索时默认走最新版本，也可指定历史版本

### 5.2 分块哈希增量同步流程

```
用户上传/修改论文草稿
        │
        ▼
┌──────────────────────────┐
│ Step 1: 文档解析          │
│ pdfplumber/nougat解析     │
│ 提取章节结构+正文          │
└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────┐
│ Step 2: 按章节分片         │
│ 每片512 tokens + 128 overlap │

└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────┐
│ Step 3: 计算分片哈希       │

│ 新版哈希 vs 旧版哈希        │
│ ┌──────────────────────┐ │
│ │ 相同hash → 复用旧向量  │ │
│ │ 不同hash → 重新嵌入    │ │
│ │ 新增hash → 新嵌入入库  │ │
│ │ 旧版独有hash → 标stale │ │
│ └──────────────────────┘ │
└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────┐
│ Step 5: 执行增量更新       │
│ · 变化分片 → 调用embedding │
│ · 写入Chroma（新collection │
│   或同collection带version）│
│ · 更新Neo4j分片索引        │
│ · 记录PaperVersionMeta    │
└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────┐
│ Step 6: 返回同步报告       │
│ {new/modi/del/unch}      │
│ + 嵌入API调用费用统计       │
└──────────────────────────┘
```

### 5.4 成本估算

以一篇8000字的中文教育论文为例：

| 步骤 | 数量 | 成本 |
|------|------|------|
| 分片数 | ~20-30 chunks | — |
| 嵌入API调用(OpenAI) | 20-30次 | ~$0.0005（可忽略） |
| 嵌入本地(bge-large) | 20-30次 | 免费，耗时~2-5秒 |
| 修改10%内容后增量同步 | 2-3次嵌入调用 | 近乎免费 |
| Neo4j三元组抽取 | ~50-100个三元组 | LLM API调用，约$0.01-0.05/篇 |

**结论：个人知识库的增量同步成本极低。** 一篇论文全量索引入库成本约$0.05-0.10（使用OpenAI API），增量修改几乎免费。本地部署bge模型则完全免费。

```

  │
```

## 九、检索质量保障

### 9.1 混合检索策略

```python
# 默认采用混合检索：向量语义 + BM25关键词
# 两路召回 → RRF(Reciprocal Rank Fusion) 融合 → MMR重排序

def hybrid_retrieve(query, project_meta, top_k=5):
    # 1. 向量检索
    vector_results = chroma.similarity_search_with_score(query, k=top_k*2)

    # 2. 关键词检索（可选Elasticsearch或Chroma metadata过滤）
    keyword_results = keyword_search(query, k=top_k*2)

    # 3. RRF融合
    fused = reciprocal_rank_fusion(vector_results, keyword_results, k=60)

    # 4. MMR重排序去冗余
    final = mmr_rerank(query_embedding, fused, lambda_param=0.7, top_k=top_k)

    return final
```

### 9.2 检索质量自评指标

| 指标 | 计算方式 | 目标值 |
|------|---------|--------|
| 检索命中率 | 检索到了至少1条相关证据的查询比例 | >90% |
| MRR (Mean Reciprocal Rank) | 第一个相关结果的排名倒数均值 | >0.7 |
| 证据溯源定位率 | 能定位到原文位置的证据比例 | 100% |
| 检索平均耗时 | 从query到返回结果的端到端时间 | <3秒 |

## 十、完整业务流程（全链路串联）

### 10.1 项目启动流程

```
1. 用户打开项目 → 前端调用 run_research_project(project_meta, user_input)
2. 调度器初始化 ResearchState
3. 自动执行 load_long_term_memory()，预加载历史证据 + 决策记录到 state
4. 进入 INTAKE 阶段
5. 调度器驱动导师规划Agent进行需求分析
6. 人工确认 ResearchContract → 进入 SEARCH_PROTOCOL_APPROVED
7. 证据综述Agent调用 global_retrieve 检索文献
8. 新证据通过 save_evidence_to_long_memory 持久化到私有知识库
9. ... 后续阶段依次执行
10. 每轮结束：compress_short_memory() + persist_state()
11. 阶段验收失败 → REWORK 分支，读取历史记忆重新迭代
12. 关键节点 human_approval_needed → 等待人工确认
```

### 10.2 论文修改同步流程

```
1. 用户在前端修改论文草稿
2. 前端调用 sync_user_paper_to_kb(project_meta, new_content, paper_id)
3. 后端执行分块哈希增量同步（详见第五章）
4. 返回同步报告（变化分片数、API费用）
5. 下次 global_retrieve 自动检索到最新版本的论文内容
6. 用户可通过 get_paper_versions 查看所有历史版本
7. 需要时可通过 rollback_paper_version 回滚到旧版本
```

### 10.3 跨会话记忆复用流程

```
会话1:
  用户研究AI在STEM教学中的应用
  → Agent产出证据 + 人工决策
  → save_evidence_to_long_memory() 持久化
  → persist_state() 保存完整上下文

会话2 (几天后):
  用户重新打开同一项目
  → load_long_term_memory() 自动加载历史证据+决策
  → state预填充历史记忆
  → 用户："上次我们确定的检索策略还适用吗？"
  → Agent读取 short_memory_summary.pinned_decisions
  → 回复："上次您在阶段SEARCH_PROTOCOL_APPROVED确认了..."
  → 实现真正的跨窗口记忆复用
```

## 十二、全局强制约束清单

| # | 约束内容 | 违反后果 |
|---|---------|---------|
| 1 | 所有接口必须透传 `ProjectMeta`，禁止缺失 `user_id` / `project_id` | 数据隔离失效，用户数据交叉污染 |
| 2 | 证据统一使用 `EvidenceItem` 结构，禁止自定义证据字段 | 证据账本格式不一致，无法统一检索 |
| 3 | Agent仅读写自身 `output_xxx` 分区，禁止修改 `current_stage`、记忆字段 | 流程状态被意外篡改，上下文漂移 |
| 4 | 检索/记忆/持久化统一调用公共API，禁止直连 Neo4j/Chroma/PG | 绕过权限控制，数据一致性破坏 |
| 5 | 流程切换/记忆压缩/状态持久化仅由LangGraph调度器执行 | 多Agent竞争导致状态不一致 |
| 6 | 长期记忆写入仅限证据综述Agent，其余Agent只读 | 非证据内容污染长期记忆 |
| 7 | 所有记忆/知识库数据必须携带 `source_type` + `verify_status` 溯源标记 | 无法区分可信证据与生成内容 |
| 8 | 论文同步必须通过 `sync_user_paper_to_kb`，禁止直接操作向量库 | 版本混乱，增量同步失效 |
| 9 | 任何Agent产出不得标记为 `human_verified`，该标记仅由人工审批节点设置 | 虚假核验，科研诚信风险 |
| 10 | 检索结果必须标注 `retrieval_metadata`（命中数/耗时/重排序信息） | 检索质量无法评估和优化 |
